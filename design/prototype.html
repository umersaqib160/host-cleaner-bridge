Open question for the client — property access

This screen assumes any cleaner on the list can get in. If entry depends on a physical key held by one person, the fallback order below is fiction — we would need a "who holds the key" field and the cascade would have to respect it. Worth asking before this is built.

Open question — when the clean actually happens

Jobs are triggered by checkout here. If the client cleans the day before the next arrival instead, the trigger changes and the "Next guest" date becomes the scheduling anchor, not the checkout.

This screen is the alternative to building an app

Everything a cleaner needs — job details, access code, accept or decline — arrives through a link in the text they already receive. No install, no store review, no adoption problem. If the client says their cleaners would not tap a link from an unknown number, this whole approach needs rethinking, which is why it is on the discovery list.

The access code is doing a lot of work here

A lockbox code makes reassignment trivial — any cleaner in the fallback order can be sent. A physical key handed between people would break it. The prototype assumes a lockbox; confirm with the client.

Declining is a first-class action, not a failure

Tapping "Hoy no puedo" costs nothing and immediately advances the cascade — far better than silence, which forces a 15-minute timeout before the next cleaner hears anything. The copy should make declining feel normal, so cleaners actually use it.
